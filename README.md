# Лаб 3: Чанарын сценарио → SLO → k6 threshold

F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

## Орчин
- node: v22.23.5
- k6: v0.55.0 (go1.23.3, linux/amd64)
- express: ^5.3.0
- OS: Ubuntu Linux

## Ажиллуулах
```bash
npm install express
node server.js                          # нэг терминал дээр
mkdir -p results && k6 run slo-test.js 2>&1 | tee results/pass.txt
```
FAIL хувилбар: `k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=$?"`

## 3 сценарио (6 хэсэгт формат)

### 1. Performance
- **Тойм:** Хэрэглэгч сагсанд бараа нэмнэ.
- **Системийн төлөв:** Хэвийн ачаалал, сервер ажиллаж байна.
- **Орчны төлөв:** localhost, Node.js + Express, k6 20 VU.
- **Гадаад өдөөлт:** 1 минутын турш 20 VU `POST /cart/add` дууддаг.
- **Шаардлагатай хариу:** Хүсэлтийн 95% нь 200 мс-ээс хурдан хариулна.
- **Хэмжүүр:** p95 latency.

### 2. Reliability
- **Тойм:** Хэрэглэгч төлбөр төлнө.
- **Системийн төлөв:** Хэвийн ачаалал.
- **Орчны төлөв:** /pay нь санамсаргүйгээр ~5% хүсэлтэд 500 буцаадаг.
- **Гадаад өдөөлт:** 20 VU `POST /pay` давтан дууддаг.
- **Шаардлагатай хариу:** Алдааны хувь босгоос хэтрэхгүй.
- **Хэмжүүр:** error rate.

### 3. Availability
- **Тойм:** Сервер гэнэт зогсоод дахин асна.
- **Системийн төлөв:** Ачаалалтай үед.
- **Орчны төлөв:** Ctrl+C / kill-ээр 10 секунд зогсоож, дахин асаана.
- **Гадаад өдөөлт:** 2 минутын тест дундуур серверийг унагана.
- **Шаардлагатай хариу:** Хүсэлтүүдийн дийлэнх нь амжилттай.
- **Хэмжүүр:** амжилттай хүсэлтийн хувь (checks).

## SLO хүснэгт
| Сценарио | SLI | Босго | Цонх | Үндэслэл |
|---|---|---|---|---|
| Performance | /cart/add p95 latency | < 200 мс | 1 мин тест | Сагсанд нэмэх нь хэрэглэгчийн мэдрэхүйц хурдтай байх ёстой |
| Reliability | /pay error rate | < 8% | 1 мин тест | Сервер 5% алдаа өгдөг тул 8% нь санамсаргүй хэлбэлзлийн нөөцтэй |
| Availability | амжилттай checks | ≥ 90% | 2 мин тест | Богино унтралтыг тэсвэрлэх зорилго |

**Error budget:** 2 минут × 10% = **12 секунд** зогсолт зөвшөөрнө.

## Үр дүн
| Туршилт | Файл | p95 /cart | /pay error | checks | Дүн |
|---|---|---|---|---|---|
| Хэвийн | results/pass.txt | 1.54 мс | 3.97% | 98.67% | PASS |
| Chaos | results/chaos.txt | 1.32 мс | 14.91% | 88.00% | FAIL |
| Зориуд FAIL | results/fail.txt | 1.66 мс | 6.00% | 97.99% | FAIL (exit=99) |

Chaos үед p95 latency хэвийн хэвээр (амжилттай хүсэлтүүд хурдан), харин серверийг унагасан хугацаанд холболт татгалзсанаас error rate болон availability муудсан.

## Дүгнэлт
Энэ лабораторид сценарио → SLO → threshold гинжийг k6-аар автоматжуулж үзлээ. Performance сценарийн /cart/add endpoint-ийн p95 нь 1.54 мс гарч, 200 мс-ийн SLO-г бүрэн хангасан. Reliability сценарийн /pay endpoint-ийн error rate 3.97% байсан нь сервер санамсаргүй 5% алдаа буцаадагтай нийцэж, 8%-ийн босгод багтсан. Босгыг 5%-тай яг тэнцүү биш 8% гэж тавьсан учир нь хэт нарийн босго санамсаргүй хэлбэлзлээс болж худал FAIL өгдөг. Availability сценарийн chaos туршилтаар серверийг 10 секунд зогсоход checks 88.00% болж 90%-ийн SLO-оос доогуур унасан. Error budget нь 2 минутын 10% буюу 12 секунд, зогсолт 10 секунд байсан ч /pay-ийн өөрийн 5% алдаа нэмэгдсэн тул нийт budget хэтэрсэн. Мөн chaos үед /pay-ийн error rate 14.91% болж Reliability threshold ч FAIL болсон нь нэг эвдрэл хоёр SLO-г нэг зэрэг зөрчиж болдгийг харуулж байна. Зориуд /report-ын threshold-ыг p95<100 мс болгоход p95 нь 388 мс гарч FAIL болсон бөгөөд k6 exit code 99 буцааж, CI pipeline-ыг зогсоож чадахыг батлав. Хамгийн их сурсан зүйл нь SLO-г тоогоор тодорхойлбол чанарын шалгалтыг автоматжуулж болдог явдал юм. Chaos туршилт нь availability сценарийн хэмжүүрийг бодитоор батлахад хэрэгтэй гэдгийг ойлгосон. Цаашид threshold-уудыг таамгаар биш бодит хэмжилтэд тулгуурлан тохируулна.
